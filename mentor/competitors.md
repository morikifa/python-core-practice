# Анализ конкурентов и профиля рынка (Competitors)

**Дата обновления:** 05.09.2026
**Назначение:** понять, чем отстраиваться от массы кандидатов, и не повторять их ошибок.

> ⚠️ **Статус данных:** все количественные утверждения ниже перенесены из истории основного чата **без указания источника** и помечены как `не верифицировано`. Не использовать их в резюме, откликах и разговорах как факты. Перед применением — найти первоисточник ≤12 мес или убрать цифру. Актуальных данных по рынку на 09.2026 в рабочем пространстве не найдено.

## 1. Типовой профиль конкурента-джуна (что делают все и почему это не работает)

| Признак | Почему это минус в глазах нанимающего |
| :--- | :--- |
| Портфолио: TODO на Django/Flask, бот с погодой, калькулятор, клон блога | Нет доменной сложности → нечего обсуждать на интервью, кандидат неотличим от 500 других |
| 0% coverage, нет тестов | Сигнал: «мой код никто не проверял, я не умею проверять сам» |
| Нет Docker | Не умеет воспроизвести окружение → нагрузка на команду |
| Один коммит «Initial commit» со всем проектом | Невозможно оценить ход мысли; подозрение на копипасту |
| Захардкоженные токены в коде | Прямой признак незнания базовой безопасности — часто автоотказ |
| Пустой GitHub-профиль, ссылки ведут на `settings/installations` | Неработающая ссылка = минус к внимательности |
| Позиционирование «готов учиться всему за еду» | Сигнал низкой ценности: работодатель ищет того, кто закроет задачу, а не того, кого надо учить |

## 2. Целевой профиль Матвея (Middle-Ready к месяцу 10)

| Измерение | Требование | Артефакт-доказательство |
| :--- | :--- | :--- |
| Портфолио | Проекты со сложной доменной логикой: геоданные (PostGIS), RAG с векторным поиском, фоновые задачи, highload-микросервис на Go | 4–5 публичных репозиториев |
| Инженерные практики | Docker Compose multi-service, pytest ≥70%, CI/CD, logging, `.env`, миграции | зелёные бейджи CI, отчёт coverage в PR |
| GitHub | Осмысленная атомарная история коммитов, feature-ветки + PR с описанием, README с архитектурной схемой | вкладка Insights/Contributions, ≥30 активных дней |
| Позиционирование | «Решаю бизнес-задачи: проектирую API, пишу тесты, поднимаю в контейнерах, объясняю архитектурные решения» | защита архитектуры на мок-интервью (40+ вопросов) |
| Отстройка от клона | Каждый проект — своя предметная область, свои решения; чужие готовые реализации своего проекта не смотреть (принцип №8) | записи в journal: «что придумал сам / что подсмотрел в доках» |

## 3. Практические выводы (что делать иначе)

1. **Не соревноваться в количестве технологий** — соревноваться в глубине одной связки: Python + PostgreSQL + Docker + тесты.
2. **Каждый репозиторий = кейс**, а не код: проблема → ограничения → решение → метрики → что бы переделал.
3. **Коммиты ежедневно** — самый дешёвый сигнал дисциплины, который виден без чтения кода.
4. **Читать чужой код разрешено только для ревью** (учиться находить баги), не для переноса в свой проект.
5. **Цифры в резюме — только из своих прогонов** (реальный coverage, реальное время отклика API), никогда «оценочные».
6. **Английский — не отдельный трек, а способ потребления документации**: 15 мин/день на docs.python.org с выписыванием терминов в `glossary.md`.

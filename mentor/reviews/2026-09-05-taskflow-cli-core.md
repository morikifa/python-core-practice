## 1. КРИТИЧЕСКИЕ ЗАМЕЧАНИЯ (доказаны запуском)

### C1. Потеря данных при конкурентной записи — самый серьёзный баг
`create_task` / `update_task_status` / `delete_task` работают по схеме **read → modify → write всего файла** без блокировки. Два процесса, прочитавшие одно состояние, перезаписывают результат друг друга.

**Доказательство (детерминированное):** A и B записали по задаче → в файле `['base', 'from-B']`, запись A **исчезла**.
**Доказательство (стресс, 10 реальных процессов):** в файле осталось **8 из 10** задач.

Это ровно тот сценарий, который заявлен в позиционировании: «возможность встраивания в сторонние скрипты автоматизации» → cron + ручной запуск = две параллельные записи = тихая потеря данных. **Тихая** — хуже всего: ни ошибки, ни лога.

**Как чинить (P0):** `fcntl.flock` на отдельном lock-файле вокруг read-modify-write + контекстный менеджер; либо single-writer + явная документация ограничения; минимум — повторное чтение непосредственно перед записью и сравнение версии (optimistic locking с полем `schema_version`/`revision`). На собеседовании «я знаю про lost update и вот мой flock» — это +2 уровня к оценке.

### C2. `flush()` без `fsync` → заявление про «защиту от сбоя питания» ложно
**Доказательство (статический анализ исходника):** `flush()=True`, `os.fsync()=False`, fsync каталога отсутствует.

`flush()` выталкивает данные из буфера Python в **страничный кэш ядра**. При падении процесса — да, данные сохранены. При **сбое питания** — нет: rename может попасть на диск раньше, чем содержимое файла. Документ и «Ответ кандидата» на вопрос №1 утверждает обратное («гарантированно атомарна… исключает потерю данных при сбое питания»). На собеседовании вопрос «а fsync делали?» разворачивает этот ответ в минус.

**Как чинить (P0):** `os.fsync(temp_file.fileno())` перед `replace()`, после `replace()` — `os.fsync` на fd каталога. И честно написать в ADR: «полная durability против power loss стоит одного дополнительного syscall на запись; для CLI-трекера это приемлемо».

### C3. `except Exception` подменяет тип ошибки: права доступа выдаются за порчу данных
**Доказательство:** `chmod 000 tasks.json` → `StorageCorruptedError: Хранилище данных повреждено: [Errno 13] Permission denied`.

Файл **цел**, но недоступен. Пользователь получает диагноз «данные повреждены» и лезет восстанавливать JSON, которого не существует. Отдельно: этот же `except Exception` проглатывает `ValueError` из `Task.from_dict` (см. C5) и `KeyboardInterrupt`-соседние `BaseException` не ловит — но ловит всё остальное, включая баги в самом коде.

**Как чинить (P0):** убрать широкий `except`, ловить явно: `json.JSONDecodeError` → `StorageCorruptedError`; `OSError` → отдельный `StorageUnavailableError` (или проброс); `ValidationError` → проброс как есть.

### C4. Права файла хранилища молча деградируют до `0600`
**Доказательство:** после атомарной записи `stat` даёт `0o600` вместо ожидаемых по umask `0o644`.

Причина: `NamedTemporaryFile` создаёт файл с режимом 0600, а `Path.replace()` переносит **inode временного файла** вместе с его правами. Для однопользовательского CLI это терпимо, но это неосознанное изменение прав — и на общем сервере (заявленный целевой пользователь: «серверы без GUI») это ломает доступ для группы. Плюс это классический вопрос на ревью.

**Как чинить (P1):** после `replace()` — `os.chmod(target, 0o644 & ~umask)`; либо создавать временный файл через `os.open(..., O_CREAT|O_EXCL, mode)` с нужным режимом.

### C5. `str()`-коэрция в `from_dict` уничтожает валидацию
**Доказательства:**
- `title=None` в JSON → `Task.title == 'None'` — задача с заголовком «None» создана, ошибки нет.
- `title=[1,2]` → `'[1, 2]'`.
- `id=12345` → `'12345'` (и это проходит как «валидный UUID»).
- `tags="backend"` (строка вместо списка) → `['a','b','c','d','e','k','n']` — тег распилен на буквы.
- `priority="urgent"` → **`ValueError`**, а не `ValidationError`: исключение стандартной библиотеки протекает наружу, минуя заявленную «единую иерархию TaskFlowError».

Это **антипаттерн «защитного программирования» наоборот**: документ заявляет Defensive Programming, а код принудительно приводит любой мусор к строке и делает его валидным. Правильно: проверять тип (`isinstance(x, str)`), а не приводить.

**Как чинить (P0):** в `from_dict` — явные проверки типов с выбросом `ValidationError`; `Priority(...)` обернуть в try/except с конвертацией в `ValidationError`; для `tags` — `isinstance(raw, list) and all(isinstance(i, str) for i in raw)`.

### C6. Заявленного тайм-трекинга не существует
**Доказательство:** поля `Task` = `['created_at','description','id','priority','status','tags','title','updated_at']`. Пересечение с `{started_at, finished_at, time_spent, duration, sessions, estimation}` = **пусто**. `stats` считает только количество задач по статусам.

Позиционирование документа: «учёт рабочего времени», «тайм-трекер», «мгновенное управление задачами и тайм-трекингом», в `--help` написано «Профессиональный менеджер задач и тайм-трекер». Фактически: **это todo-list**, то есть ровно тот проект, который рекрутеры называют «делают все джуны». Это не мелкая неточность — это обрушение единственного заявленного отличия от клонов.

**Как чинить (P0, и это же — спасение идеи):** доменная модель времени. `TimeEntry(started_at, stopped_at)` список внутри задачи + `taskflow start/stop` + `report --day/--week` (часы по задачам и тегам) + экспорт CSV. Объём — ~1 день, архитектурно ничего не ломает, а проект перестаёт быть todo-листом.

## 2. СЕРЬЁЗНЫЕ ЗАМЕЧАНИЯ (доказаны запуском)

### S1. Таблица в `list` разъезжается: `{:<16}` считает байты ANSI-экранирования
**Доказательство:** `LOW` → видимая ширина строки 66, `CRITICAL` → 67; в реальном выводе колонка приоритета выглядит как `LOW     |` / `CRITICAL |` / `MEDIUM  |` — разделители не выровнены.
**Причина:** `\033[90mLOW\033[0m` — это 16 «символов» для Питона, из них видимых 3. Формат дополняет строку до 16 *сырых* символов.
**Фикс (P1):** считать видимую ширину (`len(re.sub(r"\033\[[0-9;]*m", "", s))`) и дополнять вручную, либо собрать строку без цвета и раскрасить в конце.

### S2. ANSI-коды пишутся в stdout, даже когда это не терминал
**Доказательство:** при `isatty() == False` вывод = `'\x1b[92m[+] Задача успешно создана:\x1b[0m ID=…'`.
**Почему критично для позиционирования:** заявлено «встраивание в сторонние скрипты автоматизации». Любой `taskflow list | grep`, `> report.txt` или вызов из CI получает мусорные байты. Это прямое противоречие между заявлением и кодом.
**Фикс (P1):** `use_color = sys.stdout.isatty() and not os.getenv("NO_COLOR")` + флаг `--no-color`; отдельный флаг `--json` для машинного вывода (без него автоматизация невозможна в принципе).

### S3. Пустой префикс матчит все задачи и даёт бессмысленную ошибку
**Доказательство:** `get_task_by_id("")` при 3 задачах → `ValidationError: Префикс '' неоднозначен и соответствует 3 задачам.`
`"".startswith("")` == True для любой строки. Пользователь, нажавший Enter без аргумента (или скрипт с пустой переменной), получает сообщение про «неоднозначность», а не про пустой ввод.
**Фикс (P1):** `if not clean_id: raise ValidationError("ID не может быть пустым")` + минимальная длина префикса (4) + при неоднозначности **выводить список кандидатов** с заголовками, а не только их число.

### S4. Сортировка по `status` — алфавитная, по `title` — регистрозависимая и без учёта локали
**Доказательство 1:** `sort_by="status"` → `['cancelled','done','in_progress','todo']`. Это алфавит, а не жизненный цикл. Работает только потому, что `Status(str, Enum)` наследует сравнение строк; для «чистого» Enum был бы `TypeError`.
**Доказательство 2:** `sort_by="title"` на `["яблоко","Apple","банан","Zebra","арбуз"]` → `['Apple','Zebra','арбуз','банан','яблоко']` — латиница всегда раньше кириллицы (порядок кодовых точек), регистр ломает порядок. Для русскоязычного CLI это видимый баг.
**Фикс (P1):** словарь весов для `status` (как уже сделано для `priority`); для `title` — `key=lambda t: t.title.casefold()`, при необходимости `locale.strxfrm`.

### S5. Словарь весов приоритета — скрытая мина
`priority_weight` содержит 4 ключа. Добавление `Priority.BLOCKER` → `KeyError` в рантайме, а не на старте. Плюс словарь объявлен внутри функции и пересоздаётся на каждый вызов.
**Фикс (P2):** порядок задавать самим Enum (`PRIORITY_ORDER = {p: i for i, p in enumerate(Priority)}` на уровне модуля) или `IntEnum`; покрыть тестом на «все значения перечисления учтены».

### S6. Двойное чтение диска на одну операцию
**Доказательство:** `update_task_status` → `load_all()` вызван **2 раза** (первый в самом методе, второй внутри `get_task_by_id`). Аналогично в `delete_task`.
Не катастрофа для CLI, но (а) удваивает I/O, (б) создаёт два **разных** списка объектов в памяти — рассинхрон состояния, который маскируется сравнением по `id`, (в) на ревью это читается как невнимательность.
**Фикс (P1):** `get_task_by_id(tasks, task_id)` — принимать список как параметр, либо один `load_all()` в начале операции.

### S7. `logging.basicConfig()` на уровне модуля
**Доказательство (чистый процесс, без pytest):** до импорта `root.handlers == []`, после импорта `taskflow.cli` → `[<StreamHandler <stderr>>]`.
Библиотека переконфигурирует логирование **всего процесса-хозяина**. Если этот модуль импортируют из FastAPI или бота (а документ именно это и обещает: «сервис можно обернуть в REST API без переписывания»), он сломает чужую настройку логов. Под pytest `basicConfig` наоборот **не срабатывает** (root уже имеет handlers) — то есть поведение differs между тестами и продакшеном.
**Фикс (P0 по архитектуре):** `basicConfig` — только в `main()` или в `if __name__ == "__main__"`; лучше `logging_conf.py` с функцией `setup_logging(verbose: bool)`.

### S8. Утечка временных файлов при сбое записи
**Доказательство:** при исключении внутри `json.dump` в каталоге остаётся `tmp8q55l7mh.tmp`. `delete=False` + отсутствие `try/finally` с `unlink()`.
За месяц ежедневного использования в `~/.taskflow/` накапливается мусор.
**Фикс (P1):** `try/except: temp_path.unlink(missing_ok=True); raise`.

### S9. Метки времени не валидируются
**Доказательство:** `created_at="вчера примерно в пять"` принят без ошибки; после сортировки порядок = `['2026-09-05T14:46:05.114086+00:00', 'вчера примерно в пять']`.
Строковый тип + отсутствие парсинга = «сортировка по времени» сортирует строки. Любая ручная правка файла или миграция из другого формата ломает порядок молча.
**Фикс (P1):** валидировать `datetime.fromisoformat()` в `__post_init__`, хранить `datetime` (а сериализовать в ISO при `to_dict`); сортировать по объектам, а не по строкам.

### S10. I/O в конструкторе
`JsonTaskStorage.__init__` → `_ensure_storage_ready()` → `mkdir` + запись файла. Конструктор с побочными эффектами: нельзя создать объект в тесте без файловой системы, нельзя отложить инициализацию, ошибка диска падает на строке `JsonTaskStorage(...)`, а не на операции.
**Фикс (P2):** явный метод `ensure_ready()` или ленивая инициализация при первой записи.

### S11. `--storage` обязан стоять ДО подкоманды
**Доказательство:** `taskflow list --storage PATH` → `SystemExit(2)`, `error: unrecognized arguments`. Работает только `taskflow --storage PATH list`.
Это стандартная ловушка argparse с глобальными флагами и субпарсерами; пользователи и скрипты будут спотыкаться.
**Фикс (P2):** `parents=[common_parser]` для всех субпарсеров, либо дублировать флаг в каждую подкоманду.

### S12. Нет схемы/версии формата файла
JSON — голый массив объектов. Нет `"schema_version": 1`, нет обёртки `{"version":…, "tasks":[…]}`. Любое будущее изменение формата (например, добавление `time_entries` в C6) потребует угадывания версии по наличию полей.
**Фикс (P1, делать сразу):** обёртка с версией + функция-мигратор. Это 20 строк и сильная строка в ADR.

## 4. АНТИПАТТЕРНЫ (сверх конкретных багов)

1. **God Document.** 1000 строк «полного разбора» до написания первой строки кода. Документация обгоняет реализацию на бесконечность — это имитация работы. Порядок по принципу №9 обратный: код → тест → коммит → потом документация.
2. **Сгенерированный код, принятый без проверки.** Нарушение принципов №7 и №8. Ни один из 22 дефектов не был замечен, потому что код не запускался.
3. **Заявление без артефакта.** «Dockerfile multi-stage», «ADR создан», «91% покрытия» — глаголы совершенного вида при отсутствии файлов.
4. **Преждевременная документация собеседований.** Раздел «Вопросы на собеседовании» с готовыми ответами написан до того, как появился опыт, который защищают. Заученный ответ на `fsync`-вопрос развалится на первом уточнении.
5. **Широкий `except Exception`** в двух местах (`storage.load_all`, `cli.main`) — маскирует баги, ломает типы ошибок.
6. **Молчаливые фолбэки**: невалидное поле сортировки → тихая подмена на `created_at` (§S20 зонд: ошибки нет, возвращены 2 задачи). Молчание вместо исключения = отложенный баг.
7. **Нарушение «одна технология за раз» в рамках одного файла**: argparse + ANSI + logging + env-переменные + цветовые словари в одном `cli.py` (152 строки, 57% покрытия). `cli.py` надо резать: `parser.py`, `render.py`, `main.py`.
8. **Смешение ответственности в `format_task_row`**: форматирование + раскраска + маппинг иконок в одной функции. Тестировать можно только через сравнение строк с ESC-кодами.

## 5. РЫНОК: актуальность, нужность, уникальность, взгляд работодателя (РФ)

### 5.1. Уникальность домена — 3/10 (документ заявлял 7/10)
Ниша CLI-менеджеров задач — одна из самых перенасыщенных в истории ПО:
- **Taskwarrior** (MIT, Linux/macOS/Windows): хуки, отчёты, JSON-экспорт, пользовательские атрибуты, 20+ лет развития. В сравнениях 2025–2026 гг. стабильно в топе CLI-решений.
- **todo.txt CLI** (GPL-3.0): plain-text, скриптуемость, версионируемость через Git; в сравнении Slant 2026 отмечен как «следует unix-философии: делает одно дело».
- **todoman**, **geek-life**, **Cat**, **Whip**, **tsk**, **Taskninja** и десятки самописных — в тредах r/archlinux (2025) люди регулярно показывают **свои** todo-CLI на C/Python.
- Для рабочего Jira-контекста существует **jira-cli**.

Вывод: «законченный CLI-инструмент со сложной валидацией» — это **не** оригинальность домена, это уровень упаковки. Оригинальность появляется только от (а) реальной доменной сложности или (б) измеряемого отличия. Ни того, ни другого в текущей версии нет: учёт времени заявлен, но не реализован (C6).

### 5.2. Нужность и актуальность для найма в РФ — 3/10 как центр портфолио
Что требуют вакансии Python Junior (обзор CareerLab, май 2026): **обязательно** — Core Python (типы, ООП, исключения, генераторы), один фреймворк (FastAPI или Django), **SQL** (SELECT/JOIN/GROUP BY), Git (ветки, PR), **HTTP/REST**; **часто** — SQLAlchemy/Django ORM, Pydantic, pytest, Docker (Dockerfile + docker-compose). Тот же обзор: «большинство кандидатов приходят без реального проекта… если есть рабочий проект на FastAPI или Django + SQL + Git — вы уже в топ 25%»; «покрытие тестами (pytest) — топ 10% кандидатов».

### 5.3. Рекрутер и техлид: два разных взгляда (и документ учитывает только первый)
- **Рекрутер (скрининг 30–60 сек):** видит бейджи, README, «91% coverage», Docker → плюс. Но название «TaskFlow / менеджер задач» попадает в категорию, которую карьерные гайды прямо перечисляют в списке «какие проекты делать НЕ нужно: ❌ To-Do List (базовый) … эти проекты делают ВСЕ джуны, они не выделяют вас; если делаете — добавьте уникальность» (hirehi, ноябрь 2025). Там же: «92% рекрутеров проверяют GitHub», «README = 50% успеха», «регулярность важнее интенсивности: 3 коммита в неделю лучше, чем 30 за один день».
- **Техлид (читает код, 20–40 мин):** открывает `storage.py` — и задаёт три вопроса: `fsync`? блокировка? что при конкурентной записи? Текущий код **проваливает** все три (C1, C2). Дальше `from_dict` со `str()`-коэрцией (C5) и `except Exception` (C3). То есть документ обещает «мгновенно выделяет из 95% конкурентов», а фактически даёт техлиду готовый набор минусов.

**Практический вывод:** проект оценивают не по наличию слоёв, а по тому, **что ты знаешь про свои ограничения**. Раздел README «Ограничения и осознанные компромиссы» (нет блокировки → почему; JSON → почему не SQLite; O(n) поиск → где граница применимости) стоит в глазах техлида дороже, чем Dockerfile для утилиты, которую никто не деплоит.

### 5.4. Фриланс-кейс — направление неверное
«Разработка консольных CLI-утилит автоматизации» как услуга продаётся, но покупают не менеджер задач, а **решение своей задачи заказчика**: парсинг конкретного сайта, интеграция с конкретной CRM, конвертация форматов. Ценовой пол рынка: Kwork — парсеры от 500 ₽, простые скрипты от ~1000 ₽; FL.ru — комплексные проекты от 5000 ₽ (обзор площадок, апрель 2026). Диапазон «5 000 – 15 000 ₽» из документа достижим только при комплексном заказе с интеграциями, и он не связан с этим проектом.

**Что реально даёт Проект №0 для фриланса:** не услугу, а **доказательство дисциплины** (тесты, CI, атомарность) — его показывают в отклике на заказ «написать скрипт автоматизации». Продающая формулировка: «пишу CLI-автоматизацию с автотестами и безопасной записью данных — пример: [repo]». Ценник входа: 1500–3000 ₽ за первый заказ ради отзыва.

### 5.5. Количественная проверка «поиска по префиксу UUID» (единственная сильная фича)
Git-подобные короткие ID — хорошая идея, но документ не оценил коллизии. Расчёт по парадоксу дней рождения для 8 hex-символов (2^32):

| Задач в хранилище | P(хотя бы одна коллизия префикса) |
| :--: | :--: |
| 100 | 0.000% |
| 1 000 | 0.012% |
| 10 000 | **1.157%** |
| 100 000 | **68.781%** |

При заявленных «до 10^4 задач» шанс неоднозначности ~1% — приемлемо, но сообщение об ошибке обязано показывать **кандидатов**, а не их число (S3). Эта таблица — готовый сильный ответ на собеседовании: «я посчитал вероятность коллизии префикса и выбрал длину 8, потому что…».
